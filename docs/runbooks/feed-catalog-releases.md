# Feed catalog release and rollback

The feed catalog owner is the API platform team. Compatibility scope is the existing `/api/v1/catalog` response contract and SDK Bindings `FeedMetadata` schema version 1; the compatibility tests exercise alias rename and retirement records plus canary and retired state projections. Consumers should pin the immutable `fc-<version>-<sha256>` snapshot returned by `GET /api/v1/catalog/snapshots`; the listing is ordered newest first and uses `nextCursor` for deterministic pagination. Snapshot detail responses carry a strong ETag and immutable cache headers. Snapshots and release state are held in process memory alongside the current catalog, so deployments must keep one API instance authoritative until catalog persistence is moved to the shared store. A restart clears this in-memory history.

Configure `CATALOG_SIGNING_KEY` with at least 32 secret characters in the deployment secret store before enabling release operations. Operators stage a snapshot with `POST /api/v1/catalog/releases/canary`, compare its ID with stable using `GET /api/v1/catalog/releases/compare/:snapshotId`, and promote only after consumer compatibility checks pass using `POST /api/v1/catalog/releases/promote`. The promotion and rollback endpoints require the admin role. The release state endpoint exposes the signed stable/canary records for audit.

Rollback uses `POST /api/v1/catalog/releases/rollback` with the `snapshotId` and signature of a previously promoted release. The API verifies the signature and prior promotion record before moving the stable pointer. Unknown snapshots, forged signatures, absent signing configuration, or missing canaries fail closed. Rollout monitoring should track snapshot IDs, canary/stable comparisons, catalog route 4xx/5xx rates, and consumer lookup failures. To roll out, deploy the API, verify snapshot pagination and ETag behavior, stage canary, then promote. To roll back, restore the last known good signed snapshot. To disable the feature, unmount `/api/v1/catalog`; existing pinned snapshot IDs remain readable only while the process retains its in-memory history.

## Provider adapter certification

The aggregator maintainers own provider adapter certification and the supported provider scope is Chainlink, Redstone, Band, and Reflector. Before an adapter contributes, run `cd services/aggregator && npx vitest run tests/source-conformance.test.ts tests/provider-certification.test.ts` from the repository root. The golden vectors exercise valid, absent, malformed, zero, and out-of-range decimal responses. Certification evidence includes parsed outcome, reported decimal scale, scaled integer value, and provider observation timestamp semantics. The transport certification harness rejects private, unlisted, and non-HTTPS endpoints and aborts probes that exceed their deadline; adapter-specific mock transport tests should still run with the same command. A failed blocking vector keeps that adapter out of production feed policy until corrected.

Adding vectors is backward compatible. Roll out by running the certification suite in CI before enabling a provider in feed policy; roll back by removing that provider's eligibility from the affected policy and restoring the prior adapter build. Monitor provider invalid-payload, timeout, and source-health metrics after activation.
