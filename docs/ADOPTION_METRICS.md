# Consumer Adoption and Retention Metrics (Issue #791)

Generated by `npm run economics:adoption` from `config/adoption-metrics.json`. Do not edit by
hand; `npm run economics:adoption:check` fails when this file is stale.

## Metric catalog

Every metric is an aggregate over API keys, never a per-consumer value, and names the
product decision it exists to support. A metric without a decision is rejected by config
validation.

| Metric | Definition | Decision it supports |
| :--- | :--- | :--- |
| `weekly_active_consumers` | Distinct API keys with at least one successful request in the ISO week (UTC) | Capacity planning and the quarterly sustainability review (demand multiplier in config/sustainability-model.json) |
| `new_consumers` | Distinct API keys whose first successful request in the ledger falls in the week | Integrator onboarding and developer-relations investment |
| `stickiness` | Mean weekly active consumers divided by distinct consumers active in the period | Whether usage is habitual (production integrations) or exploratory (trials) |
| `cohort_retention` | Share of a weekly first-seen cohort active again N weeks later, for N in retentionOffsetsWeeks | Onboarding quality, SDK investment, and churn alerts before pricing changes |
| `feed_adoption` | Distinct consumers requesting each asset in the period | Feed lifecycle decisions (promote, keep, deprecate) alongside docs/FEED_COST_AND_QUALITY_COMPARISON.md |
| `tier_mix` | Distinct consumers per pricing tier in the period | Pricing-tier design and free-to-paid conversion targets |

"Active" means at least one request with status 200–399. Anonymous traffic is counted only as a
request total; it cannot be attributed and is never part of consumer counts.

## Privacy safeguards

| Control | Setting | Effect |
| :--- | :--- | :--- |
| Input allow-list | `apiKeyPrefix`, `timestamp`, `asset`, `status`, `tier` | All other fields (IP, user agent, endpoint, query) are discarded on read and only counted |
| Pseudonymization | HMAC-SHA256 with `ADOPTION_METRICS_SALT` (≥ 32 chars), truncated to 16 hex | Raw key prefixes never leave the reader; the job refuses to run without a salt |
| Salt rotation | every 12 months | Old ledgers cannot be joined to new ones; retention history resets at rotation |
| Activity ledger | pseudonym → ISO weeks, tier, assets | The only retained intermediate; no keys, endpoints, IPs or request timestamps |
| k-anonymity | cells with fewer than 10 consumers are published as `<k` | Small cohorts, tiers and feeds cannot be singled out |
| Complementary suppression | on | A lone suppressed cell takes the next-smallest with it, so it cannot be derived from the total |
| Count rounding | to the nearest 5 | Differencing two releases reveals less about single consumers |
| Retention rates | only for cohorts ≥ 10, rounded to whole percent | Rates never describe a cohort smaller than k |
| Leak check | output scanned for every raw key and pseudonym | The job exits non-zero instead of publishing |
| Retention | raw events 30 days; ledger 13 months; aggregates 24 months | Raw events match `TELEMETRY_RETENTION_DAYS` in `docs/privacy/telemetry-retention.md` |

## Running on real usage

```
ADOPTION_METRICS_SALT=<secret from Vault> node scripts/adoption-metrics.mjs --input usage.ndjson > adoption.json
```

`usage.ndjson` is one `UsageRecord` per line. Only the aggregate JSON is written to stdout; the
salt is read from the environment and never logged. Delete the raw export after the run.

## Review procedure and completion evidence

- `node --test scripts/tests/adoption-metrics.test.mjs` (run in CI) covers normal operation,
  boundaries (exactly k consumers, population below k, single suppressed cell, rounding) and failures
  (missing or short salt, forbidden input fields, a metric with no decision, an injected leak).
- `npm run economics:adoption:check` keeps this document in sync with the code.
- Quarterly (next: 2027-02-17) the owner confirms each metric still drives its listed decision and
  removes any that do not.

## Owner, scope and limitations

- **Owner**: Economics and Ecosystem Lead (metric definitions and decisions), with observability and privacy maintainers (api/src/governance/usage-tracking.ts, docs/privacy/).
- **Scope**: API-key–authenticated REST traffic recorded by `usageTrackingMiddleware`. WebSocket
  subscribers and on-chain contract readers are not covered.
- **Limitations**: an API key is not a customer (one integrator may hold several keys); "new" means
  first seen within the ledger, so retention history resets at each salt rotation; k-anonymity and
  rounding limit but do not eliminate inference across many releases.

## Compatibility, monitoring and operational impact

- **Compatibility**: offline job and documentation only. `usage-tracking.ts`, API responses,
  telemetry and the audit log are unchanged.
- **Monitoring**: each run reports discarded-field counts, suppressed-cell counts and anonymous
  request totals; a leak-check failure exits non-zero and should page the owner.
- **Operational impact**: none on serving paths; the job reads an export and needs no database access.

## Rollout and rollback

- **Rollout**: merge; provision `ADOPTION_METRICS_SALT` in Vault for the reporting job; run the first period
  manually and review suppressed cells before sharing.
- **Rollback**: stop the job and revert the commit; delete any activity ledger written under the
  current salt.
