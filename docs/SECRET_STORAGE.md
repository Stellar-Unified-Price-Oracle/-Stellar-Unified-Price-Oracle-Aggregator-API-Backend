# Secret Storage by Environment

Issue: #628. This is the single story for where each environment keeps
credentials, who may read them, and what happens when the store is unavailable.

| Environment | Store | Credential source | On store failure |
|---|---|---|---|
| Local compose | Vault dev server (`hashicorp/vault:1.15.2`, `server -dev`) | Per-run token generated by `make dev-up` into untracked `.env.vault` | Services log a warning and use local `.env` values |
| Sandbox | Kubernetes Secret created out of band (see `k8s/overlays/sandbox/secret.example.yaml`) | `secretKeyRef` in the sandbox overlay | Pod fails readiness; no silent fallback |
| Staging | Kubernetes Secret / External Secrets from the staging secret manager (see `k8s/overlays/staging/secrets.example.yaml`) | Platform-injected `VAULT_ADDR` + `VAULT_TOKEN` | Startup fails |
| Production | Production Vault cluster, unsealed by the platform; token/AppRole delivered by the secret manager | `VAULT_ADDR` + `VAULT_TOKEN` injected at deploy time; never in git | Startup fails closed |

The `*.example.yaml` files are templates only; kustomize does not reference them.
They document the keys a platform operator must supply and must never be applied.

---

## Local development Vault

`docker-compose.yml` runs Vault in dev mode. That means:

- **Unsealed and in-memory.** It has no persistent storage; restarting the
  container destroys every secret. Do not add a data volume.
- **Loopback only.** The host port is bound as `127.0.0.1:8200:8200`. Nothing
  outside the developer's machine can reach it by default.
- **Generated per run.** No root token is committed. `make dev-up` generates a
  32-byte token into `.env.vault` (gitignored, mode `0600`), prints it, and
  passes it to compose. Re-running reuses the existing local token so data
  written earlier in the same stack remains readable.
- **No real secrets.** The dev Vault holds only throwaway API keys, webhook
  secrets, and a contract admin key for local polling. Never seed production
  credentials, customer data, or anything whose disclosure matters.

Paths used by the services (KV v2, mounted at `secret/`):

| Path | Contents | Written by |
|---|---|---|
| `secret/data/api/keys` | Local API key entries | API |
| `secret/data/webhooks` | Local webhook signing secrets | API |
| `secret/data/cors/origins` | Local CORS allowlist | API |
| `secret/data/compliance/dsars` | Local DSAR records | API |
| `secret/data/contract/admin` | Local Soroban admin key | Aggregator |
| `secret/data/database/config` | Optional local DB credentials | Operator |

To reset local state, remove the Vault container and `.env.vault`; a new token
is generated on the next `make dev-up`.

## Production Vault configuration

Production does **not** run the dev image or dev mode. The expected profile:

| Concern | Production setting |
|---|---|
| Deployment | Managed Vault cluster or HA Vault on Kubernetes, not `server -dev` |
| Seal | Auto-unseal through the cloud KMS (or Shamir with quorum-held keys); unseal keys are never stored with the app |
| Auth | Workload identity (Vault Kubernetes auth or AppRole) exchanging for a short-lived token; the bootstrap token in `VAULT_TOKEN` is supplied by the platform secret manager |
| Storage | Persistent integrated storage or Consul, backed up independently of the application |
| Paths | Same KV v2 layout as local, mounted at `secret/`, isolated per environment |
| Policies | One policy per service (`api`, `aggregator`), least privilege on the paths in the table above; no `root` policy for workloads |
| Audit | Vault audit device enabled and shipped to the central log store |

The application currently authenticates with `VAULT_TOKEN`; Kubernetes auth /
AppRole exchange is the intended replacement and must preserve the same
fail-closed behaviour. Until then the platform must rotate the injected token
and restrict it to the per-service policy.

## Fail-closed rule

`VaultClient` enforces, when `NODE_ENV=production`:

1. `VAULT_ADDR` must be set — there is no fallback to `http://127.0.0.1:8200`.
2. `VAULT_TOKEN` must be set — environment-variable fallback is disabled.
3. Known development tokens (`dev-root-super-secret-token`, `root`, `change-me`,
   `replace-me`, `vault-dev-token`) are rejected.

If Vault is unreachable or sealed, both the API and the aggregator abort startup
in production instead of silently downgrading to `.env` secrets. Outside
production the existing local fallback remains available.

## CI guard

`npm run check:secrets` (`scripts/check-no-dev-secrets.mjs`) fails when:

- a staging/production overlay or base manifest contains dev-mode Vault settings
  (`VAULT_DEV_ROOT_TOKEN_ID`, `VAULT_DEV_LISTEN_ADDRESS`, `server -dev`) or the
  known dev root token;
- a non-example staging/production manifest contains `CHANGE_ME`,
  `replace-with-*`, `example-*`, or `dev-root` placeholders;
- `docker-compose.yml` contains a literal Vault token, binds `8200:8200` beyond
  loopback, or declares a Vault data volume.

It runs in the `config-contracts` CI job. Unit tests:
`node --test scripts/tests/no-dev-secrets.test.mjs`.

## Rollout and rollback

**Rollout.** Deploy the secret-manager wiring (`VAULT_ADDR`, `VAULT_TOKEN`) and
the per-service policies before deploying a release that requires Vault. Confirm
`/api/v1/health` and `/api/v1/health/ready` on one replica, then roll out the
rest. Dev environments: run `make dev-up` once; existing developers must delete
any exported `VAULT_TOKEN` that reused the old committed value.

**Rollback.** Roll back the application image with the normal procedure; the
previous image also requires Vault in production. If Vault itself is unavailable,
restore the Vault cluster/backup rather than disabling the fail-closed guard.
Removing the guard is a security exception requiring a reviewed change, and it
must never be done by pointing production at a dev Vault.
